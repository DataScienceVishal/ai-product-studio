## Critical issues (must fix)

**C1. A non-string `why` escapes as `TypeError` and settles 0/0 (regression against R5).**
In `backend/app/ai.py:330`, `_NO_ANSWER.get(why, ...)` hashes `why`. `why` comes straight from the provider:
- `ai.py:346`: chat `choice.get("finish_reason")`
- `ai.py:359`: responses `data.get("status")`
- the responses `incomplete_details.reason`

A list or dict there raises `TypeError`. That is outside the `_parse` try (`ai.py:322`), so it reaches
`notes.py`'s `except Exception` and settles `0, 0`: the tokens Azure charged are never counted against any cap.
The user also gets a 500 instead of the friendly message. On main, the same body gave a clean, billed
`AIUnavailable`.

Fix: make `_parse` return only `str | None` for `why`. For example, set `why = x if isinstance(x, str) else None`
for each source, or treat any non-string status as `"failed"`. Add the list and dict cases to the existing
parametrised tests.

## Suggestions (should fix in the same pass, cheap)

**S-a. Usage numbers: catch `OverflowError` and clamp negatives (both pre-existing).** `ai.py:322` catches
`(TypeError, ValueError, AttributeError)`, but `int(float('inf'))` raises `OverflowError`, which escapes and
settles 0/0 just like C1. Also, `int(usage.get(...) or 0)` at `ai.py:345/353/355/367` accepts negative values.
A negative settle lowers the tenant's and the global counted usage, so a misbehaving upstream could undo
spend against the caps. Azure is a trusted upstream, so this is low likelihood, but the caps are the studio's
only protection for its $80 of credit. Fix: a `_count(v)` helper that returns `max(int(v or 0), 0)`, and
`OverflowError` added to the except tuple.

**S-b. Non-JSON or non-dict 200 bodies are still billed 0/0.** `ai.py:315-319` raise `fail()` with nothing
billed, but the new rule at `:322` says an unreadable 200 "ran, so bill what we can't read". For consistency,
bill `estimate_tokens(system, user, 0)` plus `max_output_tokens` there too.

**S-c. README.** The `AI_REASONING_HEADROOM` row is missing from the README settings table. NEXT.md already
says so. Add one line next to `AI_GLOBAL_DAILY_TOKENS` explaining that it raises the reservation per summary
from about 1.2k to about 2.7k tokens in Responses mode. Also note in "Sizing the daily AI cap" that the cap
formula is unaffected: caps count settled tokens, and the reservation is only a hold.

**S-d. `reservation_estimate` getattr default 0 (`ai.py:89`).** This works because the Protocol declares
`output_headroom` and both providers set it, but a future provider that forgets it would under-reserve without
any error. Consider dropping the getattr and reading the attribute directly, so a missing attribute fails a test.

## Builder's flagged risks, checked

- **Cap sizing with the 2.7k reservation.** It still holds. The caps and `cost-guard.sh` bound settled tokens x
  price, so the monthly ceiling is still about $6.00 against $6.10. The headroom only changes how many calls can
  be held at once: about 37 per day against the 100k global cap, about 18 against the 50k trial pool, and about
  11 against the 30k trial daily cap. That is well above `ai_calls_per_tenant_at_once`. The worst-case cost per
  call rises (2700 output tokens max), and the caps already absorb that.
- **An unparseable 200 bills the full output budget.** This is acceptable. It errs toward overcounting, it
  matches the timeout path, and it is rare.
- **`getattr` default 0.** See S-d. Not a bypass today.
