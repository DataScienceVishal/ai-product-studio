# Review: p/_starter/T-32 (managed identity follow-ups)

Reviewer run, 2026-11-23. Diff: `git diff origin/main...origin/p/_starter/T-32` (ai.py, test_ai.py, ADR 0002).

## Tests
Full backend suite against a fresh `starter_test_rev32` DB, `--junitxml`:
**223 tests, 0 failures, 0 errors, 1 skipped** (34.5 s).

## Summary
The production logic is mostly right: budget = min(remaining, 5 s), `budget <= 0` fails fast, lock wait is
bounded and raises `AIUnavailable`, failure cache is set and read under the lock, cleared on success, and only
`AIUnavailable` is cached (`_fetch` converts all httpx/parse errors). ADR wording is fine. But the headline
test for the lock is vacuous, and the failure cache can be poisoned by a caller with a tiny deadline.

## Critical issues

1. **Concurrency test does not test the lock** - `tests/test_ai.py` `test_concurrent_callers_share_one_fetch`.
   The autouse fixture `_no_sleep` (line ~14) patches `ai_module.time.sleep`, which is the global `time.sleep`,
   so `_time.sleep(0.2)` in the "slow" endpoint is a no-op. **Mutation evidence:** with the lock removed
   (`acquire` replaced by `if False`, `release` by `pass`) the test still PASSES; the same code run outside
   pytest with a real 0.2 s sleep makes 8 fetches. Fix: block with `threading.Event().wait(0.2)` or a
   `threading.Barrier`/Event the test releases, not `time.sleep`. Same root cause makes
   `_time.sleep(0.1)` in `test_lock_waiter_gives_up_at_its_own_deadline` a no-op, so that test is racy:
   if the main thread wins the lock it calls the hung handler itself (MockTransport ignores timeouts),
   waits ~5 s and fails the `< 2` assertion. Use an Event set inside the handler to know `first` holds the lock.

2. **Short-deadline caller poisons the failure cache for 10 s** - `app/ai.py` `get()`, the `except AIUnavailable`
   branch. A caller with 0.2 s left times out on the token fetch; that timeout is cached and every caller
   for the next 10 s (even with 25 s budget and a healthy endpoint) fails. Reproduced: `get(0.2)` timeout
   then `get(25.0)` raises `AIUnavailable` with no request made. Fix: don't cache a timeout whose budget was
   below `self._timeout` (or cache only non-timeout failures / responses), so only a genuinely failing
   endpoint is remembered.

## Suggestions
- **Deadline can still be overrun:** lock wait and fetch each get the full `budget`, so `get(t)` can take ~2t.
  `complete()` then calls `post(timeout=min(self.timeout, remaining()))` with a negative value; with a real
  transport httpx raises `ValueError: Timeout value out of range` (verified), which is not caught -> 500.
  Fix: pass `budget - time_waited` to `_fetch`, and re-check `remaining() < 1.0` after `get()` in `complete()`.
  (Pre-existing in spirit, but this branch claims deadline correctness.)
- `FAILURE_TTL` uses the injectable wall clock `now` (time.time); a backwards clock jump extends it. Minor;
  `time.monotonic` for the failure window would be cleaner.
- `invalidate()` does not clear `_failure`; fine, but say so in the docstring.

## Verdict
**CHANGES** - fix the vacuous concurrency test (must fail when the lock is removed) and the cache poisoning.

### Critical issue
1. **A real endpoint timeout is never cached; the test claiming it is passes only because the clock is frozen** -
   `app/ai.py` `get()`, `short=left < self._timeout` (around line 158). With the real `time.monotonic`, `left` is
   always `self._timeout - (a few microseconds)`, so it is always `< self._timeout` and every `httpx.TimeoutException`
   becomes `_CallerTimeout`. Probe with production defaults (real monotonic, `timeout=5.0`, endpoint always ReadTimeout):
   `get()` x3 and `get(25.0)` x3 each made **3 endpoint calls**, raised `_CallerTimeout` every time, `_failure` stayed `None`
   (timeouts passed: 4.99999x s). `test_a_timeout_at_the_full_budget_is_an_endpoint_failure_and_is_cached` passes only
   because `_provider`-style construction injects `monotonic=clock` (a FakeClock that does not move). Impact: with a hung
   identity endpoint (the likely outage) every AI call holds the lock for up to 5 s and they all queue behind it, which is the
   case the failure cache exists for; and a test plus the docstring state behaviour that production does not have (same
   class as the earlier vacuous lock test). Fix: decide "short" from the caller's deadline, not float equality, e.g.
   `short = timeout is not None and timeout - waited < self._timeout` (only a caller whose own remaining time was the
   binding limit is "short"), and add a test that uses the real `time.monotonic` (no `monotonic=` injection) asserting one
   endpoint call for three `get(25.0)` timeouts. Alternatively, if never caching timeouts is the chosen design, say so in the
   docstring and delete the misleading test - but then queued callers behind a hung endpoint do not fail fast.

### Suggestions (not blocking)
- `test_fetch_gets_only_what_is_left_after_waiting_for_the_lock`: `pytest.raises` inside the thread lambda fails silently
  (only a thread-exception warning). Collect the outcome in a list and assert it in the main thread.
- A `_CallerTimeout` is logged at ERROR like a real endpoint failure; WARNING (or a `caller_deadline` field) would make
  alerts less noisy.

Verdict: CHANGES - one fix: the short/full-budget timeout classification (critical 1) with a real-clock test. Everything
else from the first review is fixed and verified (246/0/1 backend, 111 vitest, lock mutation kills 3 tests).
