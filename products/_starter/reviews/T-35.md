## Flake finding (pre-existing, not caused by this branch)

The builder's first-run errors come from **two test runs sharing one Postgres database at the same time**, not from
flaky test code. `tests/conftest.py:23-38` (unchanged on this branch, so main has the same behaviour) runs
`DROP SCHEMA public CASCADE` at session start and `TRUNCATE <all tables> CASCADE` after every test. Every
worktree uses the default `starter_test` database, so a second suite running at the same time wipes the first one's rows and
schema partway through. Parallel runs (for example the T-15 and T-35 reviewers, or a builder and a reviewer) therefore
fail together.

Reproduced: two suites started 3 s apart against the same database gave
`27 failed, 257 passed, 39 errors` and `24 failed, 269 passed, 31 errors`
(for example `test_auth.py::test_duplicate_email_is_rejected_case_insensitively`, `test_login_then_logout_revokes_the_session`).
Run one at a time on the same database, the suite was green 5 times out of 5.

## Suggestions (non-blocking)

1. **S1 (new board task, studio-level):** give each run its own test database. Two options: have each run set a unique
   `TEST_DATABASE_URL` (for example `starter_test_<run-id>`, created by the test script), or have `conftest.py`
   take a Postgres advisory lock (`pg_advisory_lock`) for the whole session so runs on the same database queue
   instead of breaking each other. The lock costs one line and fails safe. Add a README line saying parallel runs need separate
   databases.
2. **N1:** `_TIMEOUT_MARGIN` sits between the class and `_ENDPOINT_SUFFIXES`. Moving it next to the other module
   constants near the top of `ai.py` would make it easier to find. This is cosmetic.
3. **N2:** the README test count will drift again. Consider writing "all pass" or having CI print the count, rather than
   hard-coding it.
