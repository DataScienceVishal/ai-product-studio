## Summary

The branch adds an optional `AZURE_OPENAI_REASONING_EFFORT` (low|medium|high, trimmed and lower-cased, validated in
both `Settings` and `AzureOpenAI`, sent as `reasoning.effort` on the Responses path only). It adds a startup guard,
`AI_DEADLINE_SECONDS + 2 <= FRONTEND_TIMEOUT_SECONDS`, and a build-time `VITE_API_TIMEOUT_SECONDS` in the frontend
(default 30). Leaving the effort unset by default is the right call for gpt-5.4-pro, which rejects `low`. Refusing
to start is better than a warning here. The payload code is correct, and chat never gets the field.

The weak point is the one the builder flagged: the two timeouts must match by hand. In the deploy path they
cannot match, except at the defaults. The guard checks the server's own claim about the browser, not the real
bundle. There are also bypasses through non-finite numbers, and one untested wiring line.

## Critical issues (blocking)

### B1. The deploy pipeline cannot set the frontend timeout, so the guard gives false assurance

Files: `Dockerfile` (frontend stage, `RUN npm run build`), `README.md:133-140`, `config.py:73-76`, `api.ts:18-24`.

- The Dockerfile has no `ARG`/`ENV` for `VITE_API_TIMEOUT_SECONDS`. Every image therefore ships a 30 s browser
  abort, whatever the operator sets. The CI and deploy workflows run a plain `docker build` with no `--build-arg`.
- The README says "raise all of them together (for example deadline 55, both timeouts 60)". An operator who does
  that via Container App env (`AI_DEADLINE_SECONDS=55`, `FRONTEND_TIMEOUT_SECONDS=60`) gets a server that starts
  happily, while the browser still aborts at 30 s. That is exactly the billed-but-abandoned case the guard exists
  to stop, and now it comes with a green light.
- Why it matters: this branch exists to make pro-model latency safe to raise. As written, the only safe setting is
  the default.

Fix: make one value the source of truth. Either option is acceptable:
1. **Preferred (runtime, single source):** the backend already serves the SPA (`spa.install`). Expose the
   server's `FRONTEND_TIMEOUT_SECONDS` to the frontend at runtime, for example as a field on an existing bootstrap
   response or a `<meta>` injected into `index.html`. Drop the build variable. Then there is nothing to keep in
   step, and the guard checks the real value.
2. **Build-time, single source:** in the Dockerfile, add a global `ARG API_TIMEOUT_SECONDS=30`. Use
   `ENV VITE_API_TIMEOUT_SECONDS=$API_TIMEOUT_SECONDS` in the frontend stage and
   `ENV FRONTEND_TIMEOUT_SECONDS=$API_TIMEOUT_SECONDS` in the runtime stage. Add a CI check (for example in
   `infra/test-deploy-workflow.sh` or a small test) that both stages use the same ARG. Update the README to say:
   raise it with `--build-arg`, never with app env alone.

Either way, fix the README line so it describes a path that works. Also note there that Vite reads `.env` from
`frontend/`, not from the product root where `.env.example` lives.

### B2. Non-finite and non-positive values bypass the startup guard

File: `backend/app/config.py:72, 76, 113`. Reproduced with the real `Settings()`:

- `AI_DEADLINE_SECONDS=nan` starts OK. `nan + 2 > 30` is False. In `ai.py:295-310`, `remaining()` is NaN, so
  `remaining() < 1.0` is never true, and `min(self.timeout, nan)` is 20. **The deadline is switched off**: two
  20 s attempts plus a pause can run about 40 s or more, against a 30 s browser abort.
- `FRONTEND_TIMEOUT_SECONDS=inf` with `AI_DEADLINE_SECONDS=1000` starts OK. The guard is switched off, and the
  frontend's `timeoutMs("Infinity")` falls back to 30 s.
- `AI_DEADLINE_SECONDS=0` or `-5` starts OK. Every AI call then fails at once with "unavailable". That was a
  pre-existing gap, but it now sits next to the new guard.
- Non-numeric, zero, negative and `nan` values for `FRONTEND_TIMEOUT_SECONDS` are already rejected (`gt=0`).

Fix: `ai_deadline_seconds: float = Field(default=25.0, gt=0, allow_inf_nan=False)` and
`frontend_timeout_seconds: float = Field(default=30.0, gt=0, le=600, allow_inf_nan=False)`. Give both a sane upper
bound. Add a parametrised test for `nan`, `inf`, `0` and `-1` on both settings.

### B3. Settings-to-provider wiring of the effort is untested

File: `backend/tests/test_ai.py:659` (`test_build_provider_passes_the_api_setting`), `backend/app/ai.py:409`.
Deleting the `reasoning_effort=` argument in `build_provider` leaves the whole suite green (run for real). That
argument is the line that makes the feature reach production. Fix: in that test, build with
`azure_openai_reasoning_effort="high"` and assert `.reasoning_effort == "high"`.

## Suggestions (non-blocking)

- **S-a. The frontend has no upper cap.** In `timeoutMs("3000000")`, 3e9 ms is more than 2^31-1, and browsers fire
  such a `setTimeout` at once. Every request would then abort immediately. Clamp it, for example to `<= 600` s,
  matching B2's `le`.
- **S-b. Effort values.** The Responses API also accepts `minimal` (gpt-5) and `none` or `xhigh` on newer models.
  Rejecting them at startup is safe, but it may block a future deployment. Consider listing them, or note in the
  README why they are excluded.
- **S-c. Test name.** `test_reasoning_effort_is_absent_when_unset_and_on_chat` (test_ai.py:849) does not test chat
  (the next test does). Rename it to `..._when_unset`.
- **S-d.** `AI_TIMEOUT_SECONDS > AI_DEADLINE_SECONDS` is accepted silently (the deadline caps it, so this is
  harmless). Consider a warning.
- **S-e.** `TIMEOUT_MS` being wired to `timeoutMs()` is not tested. If B1 option 1 is taken, the runtime value
  becomes testable through a mocked bootstrap response.
- **S-f. README table row** (README.md:94) puts two unrelated variables in one row. Split it so each has a default.

## Security

No new endpoint, auth or tenant surface. The effort value is allow-listed before it reaches the payload, so
nothing an operator sets can inject into the JSON. No secrets are logged. The startup error message holds only
numbers. Cost: no change per request, and the guard lowers the risk of billed-but-abandoned calls once B1 and B2
are fixed.

## Docs

`.env.example` and the README are clear about why the app refuses rather than warns, and about the pro-model
`low` rejection. The only wrong statement is the "raise all of them together" path (B1).
