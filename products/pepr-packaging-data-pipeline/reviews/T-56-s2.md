## How I checked correctness

- **Each attempt is charged exactly once.** A 5xx is recorded at worst case right away (`providers.py:153`). On the final 5xx the
  code raises `ProviderError` with `may_have_run=False` and no tokens (`:164`), so `extract_pdf` records nothing more. The test
  asserts exactly 3 rows.
- **A timeout after a 5xx is charged.** I ran a script with a 500 followed by `socket.timeout`, going through
  `extract_pdf` on a real benchmark PDF. The ledger had 2 estimated rows: the 5xx worst case and the timeout worst case,
  one per attempt. Timeouts are still never resent.
- **5xx followed by an unreadable 200:** the earlier 5xx row plus one `may_have_run` worst case from `extract_pdf`.
  That is one charge per attempt.
- **Re-check before a retry:** this only runs after a 5xx, and only when another attempt is left. 429 and connect errors
  add no spend, so the last check still covers the next attempt. Correct.
- **BudgetExceeded in the middle of a sheet:** it is not caught by `extract_pdf`'s `except ProviderError`. Every 5xx is
  already in the ledger at that point. `run.py:54` turns it into exit 3. Correct.
- **429 and connect errors are free:** a test covers this (no ledger file is created).
- **Spend gate:** the constructor and `complete()` both refuse without `T56_SPEND_APPROVED=1`. I checked both directly.
  Every test injects a transport, so no network call can happen.
- **Scoring:** `score.py:217` adds up ledger USD by `sheet_id`. The 5xx rows use `label=sheet_id`, so pass mark 5 includes them.
  This errs high, which is the right way round.

## Critical issues

1. **No test checks that `extract_pdf` passes the budget to the provider** (`extractor/extract.py:90`). Without
   `budget`, `AzureResponsesProvider.complete` falls back silently to the old behaviour: several billable attempts under
   one reservation. Mutation M2 shows a one-line revert would bring S2 back with every test green. This is a money
   safety control, so it needs a test of the wiring.
   **Fix:** add a test that runs `extract_pdf` on a benchmark PDF with an `AzureResponsesProvider` whose transport returns
   `500, 500, 200` (or whose cap refuses the retry). Assert that the ledger has 2 estimated rows plus 1 real row, or that
   `BudgetExceeded` is raised.

## Suggestions (not blocking)

- S-a: The retry check at `providers.py:156` reserves `max_output_tokens` but not `output_headroom`, while
  `extract_pdf:88` adds it. Azure's headroom is 0, so there is no effect today. For consistency, add `self.output_headroom` there too.
- S-b: `budget=None` silently turns off per-attempt charging. Consider making `budget` required for
  `AzureResponsesProvider.complete`, or logging a warning when it is missing. That would make M2-style regressions loud.
- S-c: The `run.py` per-sheet print line and `pred["usage"]` show only the successful attempt, not the 5xx worst cases.
  This is cosmetic, because the ledger and score are right. A note in the README would stop someone misreading it.
- S-d: Several test helpers are written on one line, e.g. `def tr(req, t, seq=iter([...]))`. The mutable default works, but it is
  easy to misread. Use a closure instead.
