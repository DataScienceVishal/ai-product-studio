## Critical issues

### C1. Stray T-15 claim from another run in `state/BOARD.md`

- **Where:** `state/BOARD.md` line 24.
- **What:** T-15 changes from `[todo] … claimed-by: -` to `[doing] … claimed-by: 20261125T021930Z-run-b5f8 @ 2026-11-25T02:20:44Z`. That claim belongs to a different run. It is not part of T-30 or T-64.
- **Why it matters:** CLAUDE.md section 9 says state files go straight to main, and product branches merge only after review. If this branch is merged later, it will either re-apply a claim that has gone stale (T-15 shows as `doing` with nobody working on it, blocking other runs for 3 hours) or conflict with whatever run b5f8 has since written to main.
- **Fix:** run `git checkout origin/main -- state/BOARD.md` on the branch and commit. Make the T-30/T-64 board updates on main as usual.

## Suggestions (non-blocking)

- **S1.** `ubuntu-latest` ships shellcheck, so in CI actionlint will also run shellcheck over every `run:` block. I couldn't check that locally (downloading shellcheck was refused, and I did not retry). Watch the first `workflow-lint` run. If existing scripts produce SC2086-style noise, fix the scripts or pass `-shellcheck=` while they are cleaned up. Don't merge with a red check.
- **S2.** The pin test misses string-form `container: <image>` and flow-style `{ uses: … }`. Neither form is used today. Either extend `IMAGE` to also match `container:\s*\S+` when the value is a scalar, or note the limit in the docstring.
- **S3.** A `docker://image@sha256:…` step would be wrongly flagged, because `PINNED` only accepts `owner/repo@sha`. Accept `docker://…@sha256:<64 hex>` as pinned if anyone uses that form.
- **S4.** All the pinned versions run on `node20`. Let Dependabot (the `github-actions` ecosystem is configured, grouped weekly) propose the node24 majors (checkout v5+, setup-node v5+, and so on). Check their inputs when it does.
- **S5.** The `# Digest refreshed by hand` comment on the postgres service is accurate, because Dependabot does not track workflow service images. Consider adding the refresh command (the token plus HEAD flow above) to the comment or to SETUP.md, so the next refresh can be checked the same way.
- **S6.** The `pull_request` `paths: ['.github/**']` filter means the check won't report on other PRs. That's fine unless someone later makes `workflow-lint` a required status check, which would then block every PR that doesn't touch `.github/`.
